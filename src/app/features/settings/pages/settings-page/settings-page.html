About

An analysis runs in two phases. The structural phase runs entirely in the Electron main process and produces a fully renderable KnowledgeModel before any AI is involved. The AI phase runs concurrently in the background and patches the model in several waves, each triggering a UI re-render.

Every piece of data the UI displays traces back to one of three tiers:

  • Structural Deterministic heuristic analysis — runs in the Electron main process, always available, no LLM required.
  • Derive Structured inference from structural results — heuristic engines that produce typed data objects, no LLM required.
  • Generate Narrative text from a language model — only present when an AI provider is configured and the generate stage completes.

The KnowledgeModel is the single source of truth for all displayed data. It is constructed by WorkspaceKnowledgeService (the only service permitted to mutate it) and flows to all pages via WorkspaceManagerService.activeWorkspace$. Pages gate their sections on the capabilities[] array — never on targetType directly.

Triggered by intelligence:processWorkspace IPC. Three sub-stages run in sequence:

D6 — Incremental Check

All file contents are hashed with FNV-1a 32-bit. Compared against the stored model hash index. Decision: no changes → return cached model (fromCache: true); ≤ 30% files changed → partial rebuild (symbol index updated, graph preserved); > 30% changed or no prior model → full rebuild.

D2/D3 — Capability Pipeline

Runs a fixed capability set per target type. A capability that throws is recorded in capabilityErrors and skipped — later capabilities still run.

  • fileParsing — PatternParser → AnalysisEngine. Every file is classified by sequential content pattern-match: [ApiController] → C# API Controller; @Component → Angular Component; export class … Service → Angular Service; SELECT → SQL Query; etc. Each match maps to a hardcoded template with fixed responsibilities, inputs, outputs, dataFlow string, and security advice. These are type descriptions, not file-specific content. Complexity is the only value computed from the actual file: Low <30 non-blank lines, Medium <75, High ≥75.
  • languageDetection — counts language occurrences; calls TechnologyDetectorEngine for framework signals.
  • symbolExtraction — builds a flat index keyed by file path: classes, methods, imports, exports, language, type.
  • folderStructure — RepositoryScannerEngine builds the folderTree hierarchy.
  • dependencyResolution — DependencyMapperEngine parses TS/JS imports (relative + @app/* alias), C# using statements, and SQL table references (FROM/JOIN/INTO/UPDATE) into a directed graph. DependencyExplorerEngine then derives hubs (inbound ≥5) and ranks all nodes by total degree.
  • dataFlowExtraction — per file: classifies role (controller/component/service/repository/http-client/state-store) from name patterns; extracts sources (HTTP verbs, @Input(), localStorage reads, route params) and sinks (@Output(), router.navigate, Subject.next()); infers interaction verb per import via method-call pattern matching (reads/writes/updates/deletes/publishes/navigates/calls).
  • multiProject — ProjectDiscoveryEngine discovers sub-projects.
  • gitAnalysis — reads branch and origin URL from disk via readGitMetadata().
  • architectureDiscovery — matches folder names against a set of known architecture patterns (Angular Feature Module, Feature-Sliced Design, Clean Architecture, MVC, etc.) using per-pattern folder indicator lists and minimum match thresholds; counts hub nodes; checks tech names for framework signals. Each detected pattern receives a confidence score. Produces ArchitecturePattern[] with confidence: null until the AI phase overwrites it.

D4 — KnowledgeModel Build

KnowledgeModelEngine converts the pipeline result into the typed KnowledgeModel. The insights layer is computed here:

  • File targets — complexity from AnalysisEngine line-count bucket; maintainability from AnalysisEngine template value; dataFlow.steps split from dataFlow string on → / ->.
  • Multi-file targets — complexity from coupling ratio (edges/nodes): Low ≤2, Medium ≤4, High >4. Maintainability: Low if >100 files AND ratio >3; High if ≤50 files AND ratio ≤2; else Medium.

The model is emitted to Angular and hub pages become renderable. ai is undefined at this point.

Kicked off immediately after the structural model arrives in Angular. Runs in the background. Results arrive in waves via manager.mergeAIResults(), patching workspace.knowledgeModel.ai and triggering a re-render each time.

Derive Tier — concurrent (all start simultaneously)

  • understanding → intelligence:systemUnderstanding — produces SystemUnderstanding plus all heuristic narrative strings in one IPC round-trip. File scope: executiveSummary/businessPurpose from AnalysisEngine templates; businessCriticality from rule table (Critical if high-risk + many deps; High if high-risk OR many deps + arch layer). Folder/repo scope: executiveSummary assembled from file count + language + tech + pattern; businessPurpose from folder presence rule (api+ui+data → full-stack; services+repos → backend); keyResponsibilities from top-6 folder names via FOLDER_RESPONSIBILITY_MAP; keyWorkflows from top-4 high-fanout graph nodes; mostImportantItems from top 5–8 nodes by inbound degree. Narrative engines run inline in the same handler: HubNarrativeEngine pass 1 (structural sentence), BusinessPurposeNarrativeEngine, CodeHealthNarrativeEngine pass 1, FolderResponsibilitiesNarrativeEngine (folder), FolderWorkflowsNarrativeEngine (folder), ResponsibilitiesNarrativeEngine (file).
  • security → intelligence:security — SecurityEvidenceEngine scans all files across 8 domains using regex patterns. No LLM here — produces raw evidence only. Domains: Secrets (8 patterns, confidence-scored 40–100, 1 candidate per file, max 15 total); SQL Injection (8 concat patterns); Authentication (9 framework patterns, counts protected surfaces + unprotected HTTP verbs); Authorization (role/policy/permission/presence counts); Input Validation (7 framework patterns); Data Access (7 ORM patterns, counts parameterised vs concatenated queries); Logging (6 framework patterns, structured logging detection, sensitive-adjacent count); Error Handling (try/catch, empty catch, global handler, stack exposure). SecurityVerificationBuilder converts domainEvidence into SecurityVerificationCheck[] (pass/warn/fail per domain) — deterministic, no LLM.
  • recommendations → intelligence:recommendations — file scope: converts AnalysisEngine risks[] and modernizations[] into Recommendation[]. Folder/repo scope: generates from graph structure — high coupling hubs (inbound ≥5, score 60–80); circular dependencies (score 85); no architecture pattern detected >20 nodes (score 50); isolated files >3 (score 25); broad scope modules outbound ≥10 (score 55); mixed low-confidence patterns (score 45). technicalDebtLevel: Critical if critical recs exist; High if high-priority >2; Moderate if any medium; else Low.
  • architecture → intelligence:architectureAnalysis (folder/repo only) — input: patterns[], dependency graph, hubs, folderTree. Computes: dominantPattern (highest-confidence pattern); hubCount (isHub === true nodes); circularDependencyCount (DFS cycle detection); couplingAssessment (Critical if hubCount/totalNodes ≥0.20, High ≥0.12, Moderate ≥0.06, else Low); evolutionRisk (scored from circular count + hub count + low confidence → High ≥4, Moderate ≥2, else Low); boundaryViolations (nodes whose names match multiple layer patterns simultaneously); layerBreakdown (nodes bucketed by layer keyword). Also re-runs CodeHealthNarrativeEngine with hub/coupling/circular metrics — overwrites ai.codeHealthNarrative.
  • dataFlow → intelligence:dataFlowAnalysis — DataFlowDiscoveryEngine traces graph paths from entry-point nodes (controller/handler/endpoint/api/route/component/page name patterns), preferring typed forward transitions (entry → processor → repository → database). Up to 8 deduplicated workflows. Per workflow: failureRisk scored from step count (≥6=+2, ≥4=+1) + bottlenecks (≥2=+2, ≥1=+1) + low confidence (<0.65=+1) → High ≥4, Moderate ≥2, else Low. extractBehaviorInsights identifies entry points, most-referenced services, repositories, and bottlenecks (above-average inbound AND outbound). FolderWorkflowsNarrativeEngine generates per-workflow narrative strings.

Hub Directive — after all derive stages settle

HubNarrativeEngine.buildDirective() reads security findings count and recommendations count to produce the actionable sentence on the hub card (ai.hubNarrative.directive).

Sequential Derive — Learning Path

Runs after hub directive because it reads from ai.understanding. File scope: 4–5 steps (Purpose → Responsibilities → Main Workflow → Most Important Parts → Broader Context). Folder/repo scope: 5–6 steps (Business Purpose → Core Workflow → Architecture → Data Movement → Critical Components → Advanced Areas). Each step includes recommendedFiles[] from graph analysis. ignoreForNow[] covers isolated files, debt hotspots, high-risk areas, test/config files, and the full file tree if >50 files.

Prompt Tier

LLMSummaryService builds one prompt per page from whichever ai.* fields are populated. All prompts share the system prompt: "You are an expert software analyst. Provide clear, accurate, and actionable explanations. Be concise but thorough." Structure: persona instruction → output format constraints (scope-specific word counts) → evidence block.

  • understanding — evidence: businessCriticality, health (complexity/maintainability/risk), coreCapabilities, keyWorkflows, criticalAreas, highRiskAreas, technicalDebtHotspots, architecture (dominantPattern, confidence, coupling, hubCount, circularDeps, boundaryViolations), mostImportantItems. Output: file = 2–3 sentences; folder = 2 paragraphs 80–130 words; repo = 3 paragraphs 160–240 words.
  • security — evidence: all 15 candidates with file/line/snippet; full domain evidence summary across all 8 domains. Output: structured JSON only — postureSummary, overallRisk, securityMaturity, findings[]. Max tokens: 4096. Angular side parses the JSON and writes findings[], overallRisk, securityMaturity back into ai.security.
  • recommendations — evidence: technicalDebtLevel, total/critical/high counts, dominant category, architecture + coupling, top-3 recommendations (title, priority, category, issueDescription). Output: file = 1–2 sentences; folder = 2 paragraphs 80–130 words; repo = 3 paragraphs 150–220 words.
  • learningPath — evidence: systemType, welcomeSummary, roadmap length, first/last step, focusFirst, businessCriticality, keyWorkflows, highRiskAreas. Output: same word counts as recommendations.
  • architecture — evidence: dominantPattern + confidence, competing patterns, coupling assessment, hub count, circular dep count, evolution risk, boundary violations, layer breakdown, raw structural detection indicators. Output: file = 1–2 sentences; folder = 2 paragraphs 80–130 words; repo = 3–4 paragraphs 180–260 words.
  • dataFlow — file scope: flow pattern label, step sequence, inputs, outputs, step descriptions. Folder/repo scope: workflow count, per-workflow risk profiles (name, step count, entry point, risk), entry points, most-referenced, data access nodes, external integrations, architecture context. Output: file = 2–4 sentences; folder = 2 paragraphs 80–130 words; repo = 3 paragraphs 160–240 words.

Generate Tier

LLMSummaryService dispatches all prompts to the configured provider. Local providers (Ollama) run sequentially — security first, then each task — to avoid overloading local hardware. Cloud providers run all tasks in parallel via Promise.all. Each call: electron.aiExplain(prompt, maxTokens) → IPC ai:explain → AiKnowledgeEngine → provider.generate(). Max tokens: 4096 for security, 2048 for all others. Timeout: 300 seconds per call. Results stored as LLMSummaryEntry { content, status, provider, model, generatedAt } in ai.summaries[key].

Each page reads from a specific slice of the KnowledgeModel. Sections gate on capabilities[] and on whether the relevant ai.* field is populated.

System Understanding

  • AI Analysis card — Generate ai.summaries.understanding.content
  • Code Health card — Structural health tier badge computed from insights.complexity + insights.maintainability; narrative from Derive ai.codeHealthNarrative (enriched after architecture stage completes).
  • Business Purpose card — Derive ai.understanding.businessPurpose + ai.businessPurposeNarrative.
  • Responsibilities panel (file/folder) — Derive understanding.keyResponsibilities[] zipped with ai.fileResponsibilitiesNarrative[] or ai.folderResponsibilitiesNarrative[].
  • Components panel (file) — Derive ai.fileComponentsNarrative — classes, methods, imports, exports built from structure.symbols.
  • Components panel (folder) — Derive understanding.responsibilityGroups[] with per-component blast radius (High/Medium/Low).
  • Key Workflows (repo) — Derive understanding.mostImportantWorkflows[].
  • Key Workflows (folder) — Derive understanding.keyWorkflows[] zipped with ai.folderWorkflowsNarrative[].

Architecture

  • AI Analysis card — Generate ai.summaries.architecture.content
  • Dependency Layer Diagram — Derive ai.architecture.architectureDiagram (Mermaid flowchart TD). Groups files into four architectural layers — Presentation, Business Logic, Data Access, and External — based on file name and path patterns.
  • File Roles — Derive files classified by structural role (controller, service, repository, http-client, state-store, component) from content signals and naming patterns.
  • Hub Nodes list — Structural relationships.dependencies.hubs[] filtered to isHub=true, top 10.

Data Flow

  • AI Analysis card — Generate ai.summaries.dataFlow.content
  • File diagram — Derive ai.dataFlowFileDiagram (Mermaid flowchart LR built from insights.dataFlow steps/inputs/outputs).
  • Inputs / Steps / Outputs (file) — Structural insights.dataFlow; step descriptions from Derive ai.dataFlowFileNarrative.stepNarrative[].
  • Metrics strip (folder/repo) — Structural graph node/edge counts from Derive ai.dataFlow.
  • Workflow diagram (folder/repo) — Derive ai.dataFlow.dataFlowDiagram (Mermaid flowchart LR).
  • Workflows accordion (repo) — Derive ai.dataFlow.primaryWorkflows[] — workflowName, entryPoint, failureRisk, stepCount, narrative. Expand a workflow to see the file-by-file chain with hop verbs and failure risk.

Security

  • AI Analysis card — Generate ai.summaries.security.content (postureSummary from LLM JSON response).
  • Security Findings — Generate ai.security.findings[] confirmed by the LLM (overwritten from raw evidence). Per finding: severity badge, category, title, file + line, issueDescription, riskExplanation, remediation.
  • Security Verification — Derive ai.security.verificationChecks[] — deterministic pass/warn/fail across 8 domains (secrets, input-validation, authentication, authorization, data-access, logging, error-handling, cryptography).

Recommendations

  • AI Analysis card — Generate ai.summaries.recommendations.content
  • Summary strip — Derive critical/high/medium counts merged from ai.recommendations.recommendations[] and ai.security.findings[].
  • Improvement Opportunities — Derive ai.recommendations.recommendations[] — ranked by priorityRank, with title, priority badge, category, affectedArea, issueDescription, whyItMatters, recommendedImprovement, expectedImpact, affectedFiles.
  • Security Fixes card — Generate ai.security.findings[] filtered to critical/high/medium, capped at 8.

Learning Path

  • AI Analysis card — Generate ai.summaries.learningPath.content
  • Learning Roadmap — Derive ai.learningPath.roadmap[] — per step: title, description, whyHere, codeLocations (file paths + line ranges), checkpoints[].

Section Availability

Three fixed section catalogues — FILE_SECTIONS, FOLDER_SECTIONS, REPO_SECTIONS — define which sections exist per scope. A section is marked available only when two conditions both pass: isSectionAvailable() (checks required data exists on the model) AND renderSectionContent() produces non-empty output. This prevents the UI offering sections that would render blank.

Content Rendering Priority

Each section renderer follows the same priority order:

  • Generate ai.summaries[key].content — LLM narrative, shown first when present.
  • Derive Structured heuristic fields — typed data from derive engines, formatted as labelled lines and bullet lists.
  • Structural Raw structural data — fallback when neither above is available (e.g. raw graph edge counts).

Repo-scope sections each have dedicated renderer methods that pull the full richness of the model: executive summary includes coreCapabilities, technicalDebtHotspots, health interpretation; architecture includes dominantPattern, layerBreakdown, boundaryViolations; data flow includes workflow risk profiles, entry points, bottlenecks; recommendations show top 5 sorted by priorityRank with issueDescription + whyItMatters + recommendedImprovement; key files prefers mostImportantItems with whyImportant descriptions over raw degree ranks.

Preview Assembly

renderPreview() assembles selected sections as numbered plain text: "N. Title\n\nContent", joined by \n\n. Sections producing empty content are silently skipped and not numbered — numbering is always contiguous. The preview panel splits this text on /(?=^\d+\. )/m to recover individual sections for display.

PDF Export

Library: jsPDF, dynamically imported. All layout is hand-drawn with raw drawing primitives — no plugins. Page geometry: A4 portrait (210×297 mm), 20 mm margins, 170 mm content width, 16 mm footer zone. Two export modes are available: Export PDF (dark theme) and Print-Friendly (light/corporate theme).

  • Cover page — full-width accent rectangle (top 72 mm), report title at 22 pt, workspace name at 15 pt, scope/date at 9 pt.
  • Section headers — 3.5×8 mm brand-accent left bar, bold 13 pt title, full-width underrule.
  • Body parsing — renderPreview() output split on \n(?=\d+\.\s) into section blocks; paragraphs split on \n\n; lines starting with [WORD] rendered as severity-coloured labels (mapped to red/amber/green by keyword); two-space-indented lines at 9 pt; plain lines at 9.5 pt.
  • Pagination — checkPage(neededMm) called before each draw. Insufficient space triggers doc.addPage(), fillPageBackground() repaints the background, Y cursor resets.
  • Footers — written last in a second pass: horizontal separator, brand label left, Page N of M right at 7 pt.
  • Dark palette — background #151927 (dark navy); brand accent #8d63ff (purple); severity: red/amber/green.
  • Print-friendly palette — white background; brand accent #6d41d9 (indigo); same severity mapping on white.

All three diagram types are generated in the Electron main process as Mermaid syntax strings stored on the model. The Angular MermaidDiagramComponent renders them on demand.

Architecture Diagram — ai.architecture.architectureDiagram

flowchart TD (top-down). Built by ArchitectureDiagramEngine after ArchitectureAnalysisEngine completes.

  • With a dependency graph (primary path) — every graph node is classified into Presentation (controller/handler/component/page), Business Logic (service/manager/engine/processor), Data Access (repository/dao/store/database), or External (client/gateway/provider/adapter). Up to 4 representative nodes per layer by highest inbound degree. Layer headers link top-down; file nodes hang off headers. Up to 12 direct cross-layer edges included. Style: purple/indigo palette (#7c3aed layer headers, #1e1b4b file nodes).
  • Fallback (no graph) — up to 4 detected architecture patterns as sequentially-linked nodes by confidence ranking.

Data Flow Diagram — ai.dataFlow.dataFlowDiagram

flowchart LR (left-right). Built by DataFlowDiagramEngine. Three paths in priority order:

  • Enriched connections — when any workflow has enrichedConnections (verbs resolved from dataFlowFacts): up to 4 workflow chains with shaped nodes and pipe-label verb edges (src -->|verb| tgt).
  • Role diagram — when graph has ≥3 nodes: nodes bucketed into Entry / Processing / Data / External (dataFlowFacts.fileRole takes precedence over name inference); up to 4 reps per role; cross-role edges with verb labels. Bottleneck nodes highlighted red.
  • Workflow summary fallback — workflow names as double-circle nodes with risk icons (⚠ High, △ Moderate), or entry points as rectangles.

Node shapes by role: Processing → double-circle; Data → cylinder; Entry/External → rectangle. Style: teal/green palette (#065f46 role headers, #0d9488 process nodes, #0369a1 store nodes) — deliberately contrasting with the architecture diagram's purple.

File Data Flow Diagram — ai.dataFlowFileDiagram

flowchart LR. Built from insights.dataFlow (steps[], inputs[], outputs[]). Three columns: input nodes (rectangle) → step nodes (double-circle) → output nodes (rectangle). Inputs connect to first step; steps chain sequentially; last step connects to each output. If no steps, inputs connect directly to outputs.

Rendering (Angular)

MermaidDiagramComponent (standalone, OnPush) receives the Mermaid string as [diagram]. On each change: dynamically imports mermaid; calls mermaid.initialize() with current theme from ThemeService (dark/default); calls mermaid.render() to produce an SVG string. The SVG is post-processed by _normaliseSvg(): extracts pixel width/height; inserts viewBox if absent; replaces fixed width/height with 100%/auto; injects inline style="max-width:{maxWidth}" — where maxWidth is an @Input() defaulting to 90% (data flow workflow and file diagrams render at 65%). The processed SVG is passed through DomSanitizer.bypassSecurityTrustHtml and bound via [innerHTML]. Rendering errors show a warning icon or are silently suppressed when the mermaid package is not yet loaded.

The AI Chat panel is a context-aware assistant embedded in the right sidebar. It can answer questions about the specific codebase that is currently loaded — not generic coding questions.

What it knows

Before every message, a context block is assembled from the active workspace's analysis results and sent alongside your question. This includes: the target name and type; primary language and detected frameworks; code health (complexity, maintainability, risk); architecture pattern and coupling; data flow pattern and primary workflows; top Critical/High recommendations; security posture; and the first learning path step. The assistant cites these by name rather than speaking in generalities.

If no analysis has been run yet, the assistant will say so and suggest running one first.

Scope and history

The context badge in the panel header shows which workspace is active. Switching workspaces resets the conversation and loads context from the new target. Chat history exists only for the current session — it is not saved between application restarts.

Suggested prompts

When the conversation is empty, four starter prompts appear. These are tailored to the active target type — file prompts ask about what the file does, dependencies, and complexity; folder prompts ask about architecture and patterns; repository prompts ask for an overview, where to start, and biggest risks. Any free-form question works once you dismiss them.

Three provider implementations are available. A fresh provider instance is created on every call so settings changes are immediately reflected — no caching. The active provider is selected via activePresetId in settings; the preset's protocol field maps to a provider class.

Ollama (local)

  • Config: ollamaHost (default http://localhost:11434), aiModel (default llama3.2).
  • Model discovery: calls /api/tags — lists installed models. testConnection() calls /api/tags then verifies the configured model name appears in the result.
  • Generate: POST to /api/chat with stream: false, think: false. 300-second timeout.
  • Sequential generation in LLMSummaryService (security first, then each task one by one) to avoid overloading local hardware.

Anthropic (cloud)

  • Config: anthropicApiKeyEncrypted (stored via Electron safeStorage — AES encryption at rest), aiModel (default claude-sonnet-5-20251101).
  • API: POST to api.anthropic.com with version header 2023-06-01. System prompt sent as top-level field (Anthropic Messages API format).
  • Suggested models: claude-sonnet-5-20251101, claude-opus-4-8-20251101, claude-haiku-4-5-20251001.
  • Cloud providers run all generate tasks in parallel via Promise.all.

OpenAI-Compatible (cloud/custom)

  • Config: openaiCompatBaseUrl (required), openaiCompatApiKeyEncrypted (optional), aiModel (default gpt-4o).
  • Calls <baseUrl>/chat/completions with stream: false. Selects http vs https based on URL protocol.
  • Works with any OpenAI-compatible server — OpenAI, local inference servers, etc.

API Key Storage

API keys are encrypted with Electron.safeStorage.encryptString() (OS keychain-backed AES) before being written to settings. The IPC handler ai:isKeyConfigured returns a boolean without decrypting. Keys are never logged or exposed to the renderer process.

IPC Channels

  • ai:explain — single prompt → provider.generate(). Used for all LLM summary calls.
  • ai:chat — multi-turn conversation. Builds chat context from the KnowledgeModel via buildChatContext(), prepends system prompt, calls provider.chat() with maxTokens 4096.
  • ai:getProviders — returns provider status array. No network call.
  • ai:discoverModels — calls /api/tags on Ollama only.
  • ai:testConnection — makes a real minimal API call to verify connectivity.
  • ai:setApiKey — encrypts and saves a plain-text key. Passing null clears it.
