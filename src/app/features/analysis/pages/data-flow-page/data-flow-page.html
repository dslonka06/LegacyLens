Workflow Diagram

Workflow Diagram shows the main paths data takes through the codebase at runtime. The diagram uses whichever level of detail is available: if the analysis captured the exact verbs at each hop in a chain (e.g. "calls", "reads from", "triggers"), those labels appear on the edges; if only the sequence of files in each workflow is known, each workflow renders as a named subgraph row; if only the raw graph exists, files are grouped by their role (Entry, Processing, Data, External); and if none of that is available, workflow names render as a simple summary.

The diagram always renders left-to-right with a teal/green palette.
Workflows

Workflows are traced by starting from entry points (controllers, handlers, pages, components) and following the dependency graph forward — where file A calls file B, B calls C, and so on — up to 6 hops deep. Each resulting chain is surfaced as a named workflow representing a path data can travel through the system.

Failure Risk is a heuristic score based on how long the chain is (longer = more things that could go wrong), whether the path passes through bottleneck files (high coupling = higher blast radius), and how confident the analysis was in the trace. The score maps to Low, Moderate, or High.

Bottleneck Nodes listed inside a workflow are files that sit in that workflow's path AND have above-average connections on both sides — many files call them AND they call many files — making them the highest-risk points in the chain.

Entry Points

Entry Points are the files where external requests or user interactions first arrive in the system. The top 5 are shown, chosen by how many other files reference them — which tends to reflect how central they are to the system's surface area.

Files are classified as entry points based on their name containing terms like "controller", "handler", "endpoint", "api", "route", "page", "component", "screen", or "view". No AI is involved — this is purely name-pattern matching.

Bottleneck Nodes

Bottleneck Nodes are files that are unusually busy on both sides of the dependency graph — more files call them than average, and they call more files than average. Both conditions have to be true simultaneously.

This matters because a bottleneck sits at a structural crossroads: a bug or breaking change in it can ripple outward in multiple directions at once, making it one of the riskiest places to make modifications.

External Dependencies

External Dependencies are files that appear to represent integration points with the outside world — third-party APIs, external services, or adapter layers. They're identified by name matching: files containing terms like "client", "gateway", "provider", "adapter", "proxy", "connector", "integration", "webhook", or "http" are flagged. Up to 8 are shown.

These are worth knowing about because their behaviour isn't controlled internally — a change in an external service or API can break the codebase in ways that no amount of internal testing will catch.
